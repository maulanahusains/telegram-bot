# Life Frontend API Plan

## Boundary and conventions

**FACT:** current API endpoints are `/health`, `/admin/*`, and `/webhook/{bot_name}`. `backend/app/core/middleware.py` returns `{ok: false, error: {code, message, request_id}}` for application errors; webhook success uses `{ok: true, status: ...}`. There is no versioned user API.

**IMPLEMENTED IN PHASE 1:** `/api/v1/` is the separate user-authenticated API namespace. It avoids collision with webhook/admin routes and gives frontend contracts a version boundary. It reuses the existing error envelope/request ID convention; user API success responses use typed schemas, not Telegram response text.

All routes below are planning contracts, not implementation requirements. They derive `owner_user_id` from authenticated server context; clients never provide it.

## Authentication boundary

| Endpoint concept | Purpose |
| --- | --- |
| `POST /api/v1/auth/telegram` | Submit raw signed Telegram WebApp `initData`; backend validates it, resolves/upserts global Telegram user, creates session, returns bootstrap/session response. |
| `GET /api/v1/me` | Return authenticated platform bootstrap identity and auth expiry; no Life profile is included. |
| `POST /api/v1/auth/logout` | Revoke/delete server session. |

Outside Telegram, `POST /api/v1/auth/telegram` rejects absent/invalid initData with an explicit unauthenticated error. Browser login is deferred, not silently replaced by an insecure user-ID parameter.

**IMPLEMENTED IN PHASE 1:** the request contains `launching_bot_name` and raw `init_data`. The name is only a lookup key: the server validates its configured/enabled runtime, uses that runtime's encrypted/decrypted credential internally to verify Telegram's `WebAppData` HMAC, then resolves global `telegram_users.id`. Responses deliberately omit internal user/bot IDs and raw session material. `GET /api/v1/me` uses the HttpOnly session cookie; future Life routes use the platform authenticated-user dependency rather than accepting an owner ID.

**IMPLEMENTED IN PHASE 2:** `GET/PUT /api/v1/life/profile`, `GET/POST /api/v1/life/goals`, `GET /api/v1/life/notification-destination-candidates`, `GET /api/v1/life/notification-destinations`, `POST /api/v1/life/notification-destination-candidates/{id}/activate`, and `PATCH /api/v1/life/notification-destinations/{id}` derive ownership solely from the platform authenticated user. Destination activation accepts a candidate ID plus optional label/default choice; raw chat IDs and owner IDs are not API inputs.

## Endpoint groups

### Today

- `GET /api/v1/life/today?date=YYYY-MM-DD` — aggregated routines/reminders, meals/macros, workout state, and upcoming notifications in the authenticated user’s timezone.
- `POST /api/v1/life/today/occurrences/{id}/complete` and `/skip` — idempotent state transitions with optional note.

Today is a read-model/use-case response, not necessarily its own table. It may call Planner/Nutrition/Fitness services; avoid frontend-side joins/calculation logic.

### Profile/settings and goals

- `GET/PATCH /api/v1/life/profile` — display profile/timezone/basic settings.
- `GET/POST /api/v1/life/nutrition-goals`; `PATCH` a current/future goal by ID — preserve effective-dated history rather than mutating past data.
- `GET/POST/PATCH /api/v1/life/notification-destinations` — ownership-scoped private/group/supergroup destination registration/default configuration.
- `POST /api/v1/life/notification-destinations/{id}/activate` and `/validate` — explicit owner action to validate bot/chat delivery eligibility and enable a destination; creation, bot installation, or launch context never activates it implicitly.

### Planner

- `GET/POST /api/v1/life/reminders`
- `GET/PATCH/DELETE /api/v1/life/reminders/{id}`
- `GET /api/v1/life/reminders/{id}/occurrences`
- optional `POST /api/v1/life/reminders/{id}/reschedule` as a named operation when changing a one-time occurrence needs auditable semantics.

Create/update payload concepts: structured title, kind, schedule type, one-time instant or constrained recurrence, timezone/default choice, destination ID, enabled. Responses include `next_run_at`, human-readable schedule representation generated by backend, and validation warnings/errors.

**IMPLEMENTED IN PHASE 3:** `GET/POST /api/v1/life/reminders`, `PATCH/DELETE /api/v1/life/reminders/{id}`, `GET /api/v1/life/reminders/{id}/occurrences`, and `POST /api/v1/life/occurrences/{id}/completed|skipped` are owner-scoped. Reminder input supports only one-time aware timestamps or strict daily/weekly recurrence, never cron or natural-language parsing.

**IMPLEMENTED IN PHASE 3.5:** the Life-first frontend uses these typed APIs from `/app/planner` and `/app/settings`. The browser submits structured date/time, weekdays, timezone, destination ID, and profile/goal fields only; it does not submit owner identity or calculate the canonical next occurrence.

**IMPLEMENTED IN PHASE 4:** Telegram callbacks are not public REST APIs. `LifeBot` resolves the verified webhook actor and calls the same owner-filtered occurrence transition used by user-facing API semantics; no callback data is interpreted as owner authority.

### Nutrition

- `GET/POST /api/v1/life/foods`; `GET/PATCH/DELETE /api/v1/life/foods/{id}`
- `GET/POST /api/v1/life/meal-templates`; `GET/PATCH/DELETE /api/v1/life/meal-templates/{id}`
- `GET/POST /api/v1/life/meal-logs?from=&to=`; `GET/PATCH/DELETE /api/v1/life/meal-logs/{id}`
- `GET /api/v1/life/nutrition/summary?from=&to=` — server-calculated daily aggregates/adherence.

Food/template/log payloads use typed quantities and explicit units. Log item snapshots are backend-created. Do not accept unvalidated natural-language meal text as the only source of truth.

### Weight and fitness

- `GET/POST /api/v1/life/weight-logs?from=&to=`; `PATCH/DELETE /api/v1/life/weight-logs/{id}`
- `GET/POST /api/v1/life/workout-schedules`; `GET/PATCH/DELETE /api/v1/life/workout-schedules/{id}`
- `GET/POST /api/v1/life/workout-completions?from=&to=`; named done/skip transition endpoints if preferred.
- `GET /api/v1/life/progress?from=&to=` — server-calculated weight/nutrition/workout series.

The post-MVP target-adjustment recommendation, if built, belongs under a goal/recommendation endpoint and must require explicit Apply/Ignore.

### Grocery

- `GET/POST /api/v1/life/grocery-lists`
- `GET/PATCH/DELETE /api/v1/life/grocery-lists/{id}`
- `POST/PATCH/DELETE /api/v1/life/grocery-lists/{id}/items[/{item_id}]`
- `POST /api/v1/life/grocery-lists/{id}/items/{item_id}/mark-bought`
- `GET/POST/PATCH/DELETE /api/v1/life/recurring-grocery-items[/{id}]`

List responses include derived estimated total only when each item’s quantity/estimate makes the calculation meaningful.

### Telegram-specific support

- The Mini App auth endpoint is the only mandatory Telegram-specific user API.
- Optional `GET /api/v1/life/telegram/launch-context` can expose sanitized launch context/default destination selection after authentication; it must not make a group owner.
- Webhook remains `POST /webhook/{bot_name}` and is not a frontend API.

## Authorization rules

1. Authentication resolves exactly one server-side `telegram_users.id`.
2. All personal Life repository operations filter by it, including nested child resources.
3. A request can select a notification destination only when it is owned and explicitly enabled by the authenticated person; server verifies the configured Life bot/chat eligibility before activation.
4. Telegram inline actions must validate both callback action target ownership and the sender’s `UserContext.internal_user_id`; a message in a shared group cannot grant another user authority over the owner’s Life data.
5. Administrative `/admin` bearer operations remain distinct from end-user session auth.

## Pagination, filtering, and idempotency

- Lists with potentially unbounded history (occurrences, meal logs, weight logs, workout completions) use cursor or bounded `limit`/`offset` pagination. Match local repository style only after API phase decides a common pagination schema.
- Date-series endpoints require bounded `from`/`to` ranges and return timezone/aggregation metadata.
- Create actions originating from frontend retries should accept an `Idempotency-Key` header (or explicit client request ID) for logs, completions, and reminder creation. Persist a scoped key/response or apply unique natural constraints. Existing `telegram_updates` idempotency does not cover browser retries.
- Completion/dismiss operations should be idempotent state transitions: repeating “complete occurrence X” returns its existing completed representation rather than creating duplicate history.

## Errors and validation

Use existing error shape and request ID. Add typed error codes such as `authentication_required`, `invalid_telegram_init_data`, `session_expired`, `life_resource_not_found`, `life_forbidden`, `invalid_recurrence`, `invalid_timezone`, `invalid_state_transition`, and `idempotency_conflict`. Return generic public messages; log sensitive Telegram validation/delivery details server-side only.

## CORS/session deployment note

**IMPLEMENTED IN PHASE 1.5 / DEC-015:** frontend code calls relative `/api/v1/*` paths using same-origin cookie credentials. The production Compose `frontend` Nginx container serves the SPA and proxies `/api`, `/webhook`, `/health`, and `/admin` to the backend service. Vite’s local-development proxy is a development-server-only bridge and does not alter backend CORS.

There is still no CORS middleware. The opaque server session is delivered with configurable `Secure`, `HttpOnly`, `SameSite` cookie attributes and is scoped to `/api/v1`; defaults are Secure + Lax. A future separate frontend origin requires an explicit credentialed origin allowlist and CSRF decision before enabling it; never use wildcard CORS with cookies.
